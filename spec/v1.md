# Source 2 DiffMod Spec — Version 1

Status is draft.

## Introduction

Source 2 mods ship as VPK packs with compiled sources.
A VPK hides what it edits.
Two VPKs that replace one file clash, and the last load wins.
A VPK holds full files, so it also hides later Valve edits to those files.
After such a game update, the author must reissue the pack by hand.

A DiffMod holds plain diffs over decompiled sources.
A diff shows what it edits.
Builders merge DiffMods at build time and flag clashes with text conflicts.
A DiffMod often still applies after a game update, since a rebuild runs it past fresh sources.
If it fails, the diff marks the exact spot that needs care.

Most mods still ship as VPKs.
A companion is a DiffMod that ships next to a VPK.
Users with no builder load the VPK as it is.
Builders use the companion to merge clashes and to repair stale files.

## Terms

- A **target** is a cleartext path that a DiffMod changes.
- A **builder** is a tool that applies DiffMods and packs the result into a VPK.
  A mod manager that reads DiffMods is a builder.
- A **mod VPK** is a VPK that a mod ships.
- A mod VPK **replaces** a game file if it holds a file at the same path.
- A **companion** is a DiffMod with a `vpk` key.
- A **plain DiffMod** is a DiffMod with no `vpk` key.
- A **plain VPK** is a mod VPK that no companion names.
- The **game copy** of a target is the file from the game VPKs.
- A **VPK copy** of a target is the file from a mod VPK.

## Specification

The key words "MUST" and "MUST NOT" mark strict rules.
An imperative sentence in a numbered rule is also strict.
The key word "RECOMMENDED" marks advice that a builder or an author can skip for a good reason.

1. A DiffMod is a UTF-8 text file with LF line ends.
2. Keep one DiffMod per file.
3. The header holds zero or more lines at the top of the file.
Each header line starts with `#`.
The header ends at the first line that starts without `#`.
4. A key line has the form `# <key>: <value>`.
Trim the spaces around the key and the value.
The keys are `spec`, `title`, `game`, `game-build`, `decompiler`, and `vpk`.
Each key appears at most once, except `vpk`.
If one of those keys repeats, builders read the first line.
Builders ignore unknown `#` lines.
Builders treat them as comments.
Compound values use the `name/version` form.
All header keys are optional.
5. The `spec` key holds the spec name and version, for example `spec: source2-diffmod/v1`.
A file without a `spec` key defaults to `source2-diffmod/v1`.
If you add a header, place `spec` first.
6. The `title` key holds a short human name.
The `game` key holds the game id, for example `deadlock`.
The `game` key routes the DiffMod to a profile.
Builders with one game ignore it.
The `game-build` key is RECOMMENDED and holds the game build id.
The `decompiler` key is RECOMMENDED and holds a registry id plus a version, for example `source2viewer-cli/20.1`.
Take ids from `decompilers.md`.
The `vpk` key marks a companion, see rule 12.
7. The body is a unified diff.
Use `diff -u` form with `---` and `+++` lines.
The body MUST apply clean with `git apply -p1` to the decompiled game files that the author used.
8. Paths MUST use `a/` and `b/` prefixes.
Paths MUST stay relative to the VPK root.
New files MUST use `--- /dev/null` plus `+++ b/<path>`.
Version 1 forbids renames.
Version 1 forbids deletes.
Use LF line ends in hunks.
9. Each target path MUST map to a compiled path through the game profile.
Each profile lists its own map.
The next table shows the Deadlock map.
Files with a raw suffix such as `.cfg` pass through with no compile step.
If no map row fits a target, fail the build.
Name the suffix in the error.

| Cleartext suffix | Compiled suffix |
| --- | --- |
| `.css` | `.vcss_c` |
| `.xml` | `.vxml_c` |
| `.js` | `.vjs_c` |

10. Decompile each target that the game VPKs hold.
Apply DiffMods in the order the user gives.
If a plain DiffMod does not apply after the earlier ones, fail the build.
Name the DiffMod and the target in the error.
Compile each result with the game resourcecompiler.
Pack compiled outputs plus raw files into one VPK.
11. The builder MUST record the game build ID from `steam.inf`.
The builder MUST record the decompiler id and version.
The builder MUST record the spec version.
Keep this record in the build log.
Builders MUST NOT need the `decompiler` key to build.
Warn on decompiler mismatch is RECOMMENDED.
Fail on decompiler mismatch is allowed but not RECOMMENDED.

### Companions

12. A companion ships next to one or more mod VPKs.
The VPKs hold the full mod and load with no build.
The companion holds the diffs for the game files that those VPKs replace.
Each `vpk` line names one VPK.
The value MUST be a bare file name with no path separator.
Resolve the name in the folder that holds the companion.
Repeat the key for each VPK.
For a pack with chunk files, name the `_dir.vpk` file.
A builder that renames a VPK MUST keep the pair in its own records.
13. A companion MUST cover each game file that its VPKs replace, if the profile lists the suffix.
The body MUST reverse apply clean to the decompiled VPK copies with `git apply -R -p1`.
Two VPKs of one companion MUST NOT replace the same game file.
A companion MUST NOT add new files.
New files stay in the VPKs.
Files with other suffixes stay outside the companion.
For those files, the last load wins.
14. Builders MUST NOT apply a companion without its VPKs.
If a named VPK is absent, skip the companion.
Warn, and name the absent VPK.
15. A companion pair needs no build by default.
Load its VPKs as they are.
Rebuild a target only for a clash, see rule 16, or for a stale copy, see rule 19.
16. A plain DiffMod changes each target in its body.
A mod VPK changes each target whose game file it replaces.
Two mods clash on a target if both change it.
If mods clash on a target, rebuild that target.
17. To rebuild a target, take the game copy as the base and decompile it.
Apply each DiffMod that covers the target, in the order the user gives.
If a companion does not apply, leave it out of that target.
Warn, and name the mod and the target.
Compile the result, and pack it into the one VPK from rule 10.
That VPK MUST take priority over each mod VPK.
New files still load from the mod VPKs.
18. A plain VPK copy has no diff.
If a plain VPK replaces the target, use its decompiled copy as the base in place of the game copy.
If two plain VPKs replace the target, use the copy that the game loads, and warn.
A VPK copy that its companion does not cover counts as a plain VPK copy.
19. Check each companion pair on install and after each game update.
Decompile each VPK copy that the companion covers.
Reverse apply the companion to those copies.
If the reverse apply fails, the pair does not match.
Warn, and treat its VPKs as plain VPKs.
If it succeeds, the result is the base that the author used.
Compare that base with the game copy.
If they differ, the VPK copy is stale and hides Valve edits.
Offer a rebuild of that target, and let the user decide.
This check and this offer are RECOMMENDED.

### Scope and versions

20. Spec version 1 covers Deadlock.
The core stays game neutral.
New titles need a profile and a build test.
Send profiles as spec pull requests.
21. Spec versions use plain integers with a v prefix: v1, v2, v3.
Builders warn on unknown spec versions and proceed.
A new integer marks a break in form or build acts.
Freeze each released version.
Never edit a frozen version.
If you fix a typo, add an erratum in the changelog.

## Advisory

This section is advisory, not strict.

Keep hunks small.
Small hunks survive game updates.
Large ones clash.
Prefer style edits over layout edits.
Style rules clash less than moved panels.
Put new panels, styles, and scripts in new files.
Hook them in with small hunks, such as one include line.
Place new files under a folder named after the mod.

A plain DiffMod needs a builder on the user machine.
A VPK with a companion loads with no builder.
Pick the form that fits your users.
Never ship a VPK that replaces game files with no companion.
Full game files hide Valve edits.
Never ship a game file that you did not change.
Name the companion after its VPK, for example `pak01_dir.vpk` and `pak01_dir.patch`.
Make the companion with a tool, not by hand.
Decompile the game copy and the VPK copy with one decompiler, then diff them.
Set the `decompiler` key in each companion.
If a game update edits a file that your VPK replaces, reissue the VPK and the companion.

Name titles plainly.
The title key serves mod lists and managers.
Name stored DiffMods with the `.patch` suffix.
Keep three lines of context.

## Example

A header looks like this:

```text
# spec: source2-diffmod/v1
# game: deadlock
# decompiler: source2viewer-cli/20.1
# title: Always show ability suggestions
```

A companion looks like this.
The VPK ships `compact_hud/main.css` as a new file.
The companion holds only the hook.
Paths are illustrative.

```text
# spec: source2-diffmod/v1
# game: deadlock
# decompiler: source2viewer-cli/20.1
# title: Compact HUD
# vpk: pak01_dir.vpk
--- a/panorama/layout/hud.xml
+++ b/panorama/layout/hud.xml
@@ -2,6 +2,7 @@
   <styles>
     <include src="s2r://panorama/styles/hud.vcss_c" />
     <include src="s2r://panorama/styles/hud_common.vcss_c" />
+    <include src="s2r://panorama/styles/compact_hud/main.vcss_c" />
   </styles>
   <scripts>
     <include src="s2r://panorama/scripts/hud.vjs_c" />
```

## FAQ

**Why diffs and not full files?**
Full files hide Valve edits and clash on each shared file.
Diffs show edits and merge.

**Does one DiffMod cover many files?**
Yes.
One DiffMod holds edits to any count of targets.

**What if a DiffMod fails to apply?**
Re-derive it from fresh sources.
The old diff shows the prior intent.

**Why the `.patch` suffix?**
Diff tools and builders read it with no extra setup.

**Why ship a VPK and a companion?**
Users with no builder drop in the VPK and play.
Builders read the companion to merge clashes and to find stale files.
Authors keep one release flow.

**Do builders use the companion on each load?**
No.
A builder rebuilds a file only if two mods change it, or if the user accepts a repair.

**What if two companions do not merge?**
The builder leaves the later one out of that file and warns.
Change the mod order to keep the other one.

**How does a builder find a stale file?**
It reverse applies the companion to the VPK copy.
The result is the game file that the author used.
If the current game file differs, the VPK copy is stale.

**Does each game update make a VPK stale?**
No.
A VPK copy is stale only if Valve edited that same file.

**Why does a companion need its VPK?**
The diffs hook in new files that only the VPK holds.
A build without the VPK points at absent files.

**Why may a companion not add new files?**
The VPK already ships them.
A second copy can drift from the first.

**What about CS2 or Dota 2?**
Version 1 covers Deadlock alone.
The core fits more titles with Panorama sources in VPKs.
Each new title needs a profile and a build test.

**Why pin the decompiler?**
Decompile output shifts with the decompiler release.
A pinned version keeps builds repeatable.
It also keeps the companion check exact.

**How do new decompiler names get issued?**
Send a pull request that adds one registry row.
Take the first free slug.
The id maps to one tool and one release line.

**Does a new decompiler need a new spec version?**
No.
New rows extend the registry, not the form.
Old files still validate, so the version stays.

**Does a new file type need a new spec version?**
No.
New suffixes extend the profile, not the form.
Prove a full round trip first: decompile, edit, compile, load.
Send the map row as a profile pull request.

**Do builders enforce the header?**
Builders read what they need and skip the rest.
Warn on unknown spec versions and proceed.
Warn on decompiler mismatch is RECOMMENDED.
